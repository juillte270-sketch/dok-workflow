# 시스템 개발 프로세스 (Development Workflow)

> Research → Plan → Annotate → Implement
> 출처: "진짜 개발자가 하는 바이브 코딩" 영상 분석 (2026-02-27)

## 핵심 원칙

**"사용자가 '구현해'라고 말하기 전까지 코드를 작성하지 않는다."**

Claude 내장 plan mode 대신 `plans/` 디렉토리에 별도 MD 파일을 작성한다.
이유: 에디터에서 직접 편집 가능, 프로젝트 산출물로 영구 보존, 컨텍스트 압축에도 유지됨.

## 적용 기준

### 이 워크플로우를 사용할 때 (시스템 개발)
- 새 스크립트 작성 / 기존 스크립트 로직 수정
- 새 디렉티브 / 스킬 생성
- mappings.json 구조 변경
- CLAUDE.md 업데이트
- 복잡한 버그 수정 (2개+ 파일 연쇄 변경)

### 사용하지 않을 때 (일상 운영)
- 일일 발주 처리 (배송리스트, 발주시트 등)
- 기존 스크립트 실행 (파라미터만 변경)
- 단순 매핑/설정값 추가 (1개 파일, 몇 줄 수정)
- 경미한 오타 수정

## Phase 1: Research (조사)

**목표**: 관련 코드와 디렉티브를 깊이 읽고, 발견한 사실을 파일에 기록.

**절차**:
1. `plans/_templates/research_template.md` 복사
2. 파일명: `plans/{YYYYMMDD}_{task_name}_research.md`
3. 관련 파일 읽기 (코드, 디렉티브, MEMORY.md)
4. 현재 동작, 제약 조건, 핵심 발견 기록
5. 열린 질문이 있으면 사용자에게 확인

**산출물**: `{date}_{name}_research.md`

## Phase 2: Plan (계획)

**목표**: 구체적인 구현 계획을 코드 스니펫과 함께 작성.

**절차**:
1. `plans/_templates/plan_template.md` 복사
2. 파일명: `plans/{YYYYMMDD}_{task_name}_plan.md`
3. 작성 항목:
   - 성공 기준 (검증 가능한 체크리스트)
   - Step별 구현 계획 (변경 전/후 코드 스니펫)
   - 대안 비교 (해당 시)
   - 영향 범위 (수정 파일 목록)
   - 테스트 계획
   - 롤백 계획
4. 사용자에게 plan.md 검토 요청

**산출물**: `{date}_{name}_plan.md`

## Phase 3: Annotate (검토)

**목표**: 사용자가 plan.md에 인라인 메모를 추가하고, 합의할 때까지 반복.

**검토 마커**:
- `[OK]` — 승인
- `[수정]` — 수정 필요 (뒤에 내용)
- `[질문]` — 확인 필요 (뒤에 질문)
- `[삭제]` — 이 항목 제거
- `[추가]` — 추가 필요 (뒤에 내용)

**반복 절차**:
1. 사용자가 plan.md에 마커 추가
2. Claude가 마커를 읽고 plan.md 업데이트
3. `[수정]`/`[질문]` 마커가 모두 해소될 때까지 반복
4. 사용자가 "구현해" 또는 동등한 승인 신호

**주의**: `[수정]`이나 `[질문]`이 하나라도 남아있으면 Phase 4로 진행하지 않는다.

## Phase 4: Implement (구현)

**목표**: 승인된 계획을 기계적으로 실행.

**절차**:
1. plan.md의 Step을 순서대로 실행
2. 각 Step 완료 후 결과 확인
3. **계획에 없는 변경이 필요하면 즉시 중단** → Phase 3으로 복귀
4. 테스트 계획 실행
5. 완료 후 plan.md의 성공 기준 체크

**규칙**:
- 계획에 명시된 파일만 수정
- 계획에 명시된 변경만 적용
- 추가 변경 발견 시: 중단 → plan.md에 추가 → 사용자 승인 → 재개

## 방향 전환 절차

구현 중 근본적으로 잘못된 방향이 발견되면:

1. `git stash` 또는 `git reset` 으로 변경 사항 보존/취소
2. plan.md에 발견된 문제 기록
3. 범위를 축소하여 새 plan 작성
4. Phase 3 (Annotate)으로 복귀

**원칙**: 잘못된 방향 위에 패치하지 않는다. 되돌리고 범위를 줄인다.

## 기존 스킬과의 관계

```
pre-prompting (성공 기준 정의)
    ↓
Research (코드베이스 조사)
    ↓
Plan (구현 계획 작성)
    ↓
Annotate (사용자 검토, 반복)
    ↓
Implement (기계적 실행)
    ↓
assetize (자산화: 디렉티브/메모리 갱신)
```

- `/pre-prompting` → Phase 1 전에 성공 기준 정의
- `/debug-5step` → Research 중 버그 원인 분석에 활용
- `/extract-essence` → Implement 후 학습 사항 자산화
- `/assetize` → 세션 종료 시 전체 자산화
